# 在庫状況チェックの開発とパフォーマンスに関する考慮事項

在庫の正確性は重要な検討事項です。 バックオーダーや在庫切れのしきい値の設定など、このリスクを可能な限り低くするのに役立つネイティブ機能がいくつかあります。 これらのトピックは両方とも[Adobe Experience League](https://experienceleague.adobe.com/en/docs/commerce-admin/inventory/configuration/backorders)で読むことができます。詳しくは、こちらを参照してください。

Adobe Commerceストアでリアルタイムの在庫状況チェックが要求されるプロジェクトやユースケースがあります。 このチュートリアルでは、開発とパフォーマンスに関する考慮事項を含め、この会話を処理するためのinsightについて説明します。

## このリクエストが必要かどうかを検証

次の質問に対して、できる限り多くの情報を提供する必要があります。 最も重要なことは、ネイティブ機能がこのプロジェクトで受け入れられないことを確認することです。 このリクエストの背後にある理由を見つけて、Adobe Commerceのネイティブ機能がこのリクエストを満たさないことを検証します。

また、この機能を開発、テスト、保守するためのコストも考慮されます。 関係者の意見は、必ずしも要件を構成するものではありません。 Adobe Commerceのコア機能の外で在庫検証を行うと、関連するコストが発生します。 これらのコストは、技術的負債、より多くのテストと検証、アーキテクチャの使用状況に関する文書やサポート文書などの形で発生します。

## 許容できるインベントリ更新の頻度の決定

在庫チェックと、それが3つのアプローチでどのように達成されるかを検討してみてください。 それぞれに利点と限界があります。 また、複雑さが増し、エラー処理に対してより多くのテストと思考が必要になります。 カスタムソリューションを導入する際には、追加の責任と考慮事項があることを忘れないでください。 例えば、フォールバックプロセス、モニタリング、テスト、トラブルシューティングなどがあり、これらは開発チームが担当します。 その際、新しいサポートドキュメント、トレーニング、モニタリング機能を導入し、開発チームが機能全体をサポートできるようにすることが重要です。 副作用として、開発チームがプロセスを所有し、コアAdobe Commerceアプリケーションが提供するネイティブ機能を活用しなくなることが挙げられます。 Adobe サポートは、このレベルのカスタマイズを支援できません。

まず、ネイティブ機能を利用します。 ネイティブ機能を利用することで、リスクを最小限に抑え、多くのメリットを享受できます。 このアプローチを採用すると、Adobe Commerceが提供するすべての既存のドキュメントとチュートリアルを利用して、この機能を使用できます。 在庫管理にはさまざまな側面があるため、最初の検討事項としてアプリケーションに付属しているものを使用してください。 ただし、注文時にコマースで見つかったデータが正確ではないユースケースがあります。 データが非同期になる例として、Order Managementシステムで直接Adobe Commerce アプリケーションの外部に営業部門が許可されることがあります。 その理由は、正確な在庫量をAdobe Commerceで表すためには、Adobe Commerce情報をできるだけ正確に保つために、何らかの統合が必要だからです。 過剰販売が許されない場合は、在庫切れのしきい値を追加することは、ゼロになる前に商品の販売を停止するための優れた方法です。 Adobe Commerceのネイティブ同期機能は、1日あたり最大1回です。 この頻度は、いくつかのユースケースでは十分ですが、他のユースケースでは十分ではありません。 詳しくは、[ スケジュールされたインポートとエクスポート ](https://experienceleague.adobe.com/en/docs/commerce-admin/systems/data-transfer/data-scheduled-import-export)を参照してください。

2つ目は`near real-time`です。 ほぼリアルタイムでネイティブ機能を使用しています。 しかし、これには、コマースを頻繁にフィードし、スケジュールどおりに在庫を更新するための統合を提供するための追加作業が含まれます。 例えば、毎時間。 このオプションでは、統合の仕組みについて考える必要がありますが、「bulk api」を使用してミドルウェアでデータの変換を行い、それをコマースにプッシュすることは素晴らしいアプローチです。 Adobe App Builderなどの基盤を利用して、作業の大部分を処理し、より頻繁にAdobe Commerceにプッシュします。

リスクと責任が最も大きい3つ目のアプローチで、最も複雑なのは、外部APIまたはデータソースに対するリアルタイムのライブインベントリチェックです。 外部システムにリアルタイムで在庫チェックを実施するのはリスクが高く、考慮すべき他の要素もいくつか存在します。 ここでは、その他にも評価が必要な項目をいくつか紹介します。

* 外部システムはRESTまたはGraphQL リクエストを受け入れることができます
* エンドポイントに対して、web サイトトラフィックと一致しない1分あたりのリクエスト数（X件）などの制限はありますか
* ロード中の応答時間はどうなるか
* 応答時間が長い場合はどうなりますか。これを自動的に終了し、ネイティブインベントリなどのフォールバックオプションを使用します。
* API リクエストが許容値制限内であることを確認するために使用できる監視のタイプ

## 非ネイティブ在庫管理の考慮事項

カスタマイズは、できるだけ複雑にしないでください。
在庫の組織がどの程度フラットになるのか、1つのSKUと利用可能な在庫の合計量か、または考慮する必要がある他の属性があります。

在庫情報がskuや利用可能な合計数量など、かなりフラットな場合は、ほぼリアルタイムのオプションが拡張されます。 ほぼリアルタイムという概念は、ソースから在庫を収集し、その後、リクエストに応答するために使用されるストレージエンジンを入力するバックグラウンド操作があることを意味します。 これには、Redis、Mongo、その他の非リレーショナルデータベースなどを使用できます。 これらのオプションは高速で、キーと値のペアに最適です。 データがもう少し複雑な場合は、コマースアプリケーションの内外でリレーションデータベースを使用する必要があります。 これをコマースデータベースからオフロードすることで、コアコマースアプリケーションをこれらのトランザクションから分離できます。 もう1つの利点は、コマースアプリケーション、CPU、RAMなどのI/Oを使用から救うことです。 Adobe Commerce アプリケーションサーバーからリソースを保存するには、新しいAPIを利用して、オフサイトストレージからデータを取得します。 このプロセスでは、あらゆるデータを変換するためのミドルウェアが必要です。 次に、呼び出し元のアプリケーションが期待どおりに結果を取得できることを確認します。 Adobe App BuilderとAPI Meshを組み合わせて使用すると、データを適切な形式で変換して返すことができます。

API メッシュでAdobe App Builderを使用することも、複数のソースから在庫を収集する場合に最適な方法です。


## 実行ロジックをプロセス外に移動

Adobe Developer App Builderは、Adobe ソリューションを拡張するためのカスタムエクスペリエンスを統合および作成するための、統一されたサードパーティ拡張性フレームワークを提供します。 Adobe CommerceはAdobe Developer App Builderを使用できます。 このアプローチは、通常コアアプリケーションで発生する一部の機能を拡張し、オフサイトに移動させる優れたユースケースです。 Commerce アプリケーションから機能を削除することで、Commerce アプリケーションのモジュール数と複雑さが軽減されます。 これにより、プロセス内でのカスタマイズ数が少なくなり、アップグレードやメンテナンスの複雑さが軽減されます。

Adobeでは、このタスクの実行方法を把握するために、優れたインスピレーション源となるドキュメントをいくつか作成し、実際に使用できるコードサンプルを提供しています。 買い物客が商品をカートに入れた際、サードパーティの在庫管理システムは、その商品の在庫があるかどうかをチェックします。 その場合は、製品を追加します。 それ以外は、エラーメッセージを表示します。 コードサンプルと詳細については、[Webhook ユースケース ](https://developer.adobe.com/commerce/extensibility/webhooks/use-cases/#add-product-to-cart)を参照してください。

## 在庫チェックを実施するタイミング

在庫がまだ利用可能かどうかを確認するのは、ビジネス関係者であり、ソフトウェアアーキテクトは他の主要な関係者からの情報を使用します。 適切なタイミングには、カートに商品を追加するタイミングやチェックアウトワークフローに入るタイミングなどがあります。 その他のイベントは、不要な場合にバックエンドシステムに負荷がかかります。 在庫の問題を特定する目的は、在庫が最も重要な場合にのみ存在することに留意してください。 在庫状況チェックの全体的な目標に影響を与えるその他のチェックを慎重に検討し、関係者が追加の負荷の潜在的なリスクを認識している場合にのみ許可します。

## 在庫ソースを調査する

外部在庫源の包括的な調査が必要です。 評価すべき項目は、使用可能なAPI オプション、GraphQLのサポート、および予想される応答時間です。 インベントリソースの接続帯域幅が制限されている場合、またはリアルタイム要求で使用することを意図していない場合、使用機能は除外され、代わりにほぼリアルタイムを考慮する必要があります。 API リクエスト時間が定義されたパラメーターを超える場合、これを実行可能なオプションから除外します。 この動作の例として、api応答は1回限りの要求に対しては200 msですが、中程度の負荷では500 ～ 900 msに上昇します。 この状況は、負荷が増え、ライブインベントリの呼び出しが利用可能になるのを除外すると、さらに悪化します。

APIの応答時間は、シンプルなリクエストと、ライブ web サイトでの予想トラフィックと同様の大量のリクエストでテストするようにしてください。 現実世界のシナリオをシミュレートするために、コマースのあらゆる領域を同時にテストすることを忘れないでください。 商品ページ、カート、チェックアウト中にライブ在庫呼び出しが発生した場合、読み込みテストでは、実際の顧客行動を模倣するために、これらすべてを同時にシミュレートする必要があります。

## 代替オプション

在庫ソースがダウンしてモニタリングが利用可能な場合は、Adobe Commerceのネイティブ機能を使用することをお勧めします。 しかし、適切に監視すれば、リアルタイムの在庫チェックの欠如を反映して、顧客体験を動的に変化させることができます。 つまり、セールやイベントが早めにキャンセルされたり、ディスプレイから削除されたりして、売り越しを防ぐことができます。 フォールバックプランについてストアオーナーと話し合い、在庫ソースがダウンした場合に自動的に引き継ぐプロセスについて、全員が理解できるようにします。

## まとめ

リアルタイムの在庫チェックの導入は、大きな決断をもたらします。 web サイトオーナーや開発チームなどが十分な教育を受け、あらゆるメリットと潜在的な落とし穴を開発者リードやアーキテクトに周知できるようにします。 慎重なプランを提供して、その理由とフォールバックプロセスを明らかにすることが、成功の鍵となります。

ライブ在庫チェックは可能ですが、QA サイクル中のテストと検証に関する調査と検討が必要です。 負荷テストとエンドツーエンドの自動化されたテストを確実に実施することで、潜在的な問題を捉えて対処できます。

監視によって失敗した呼び出しや応答時間が遅いことが検出された場合は、アクションを実行してサイトをオンラインに保ち、顧客の不満を最小限に抑えます。 フォールバックオプションは、ネイティブ機能の使用、プロモーションの無効化、開発チームへの通知、リクエストのセカンダリバックエンドシステムへの再ルーティングなど、多岐にわたります。 フォールバックメカニズムの実装方法は、あらゆるシステムがある時点で問題が発生するため、実際の統合と同様に慎重に計画する必要があります。 自動化されている、または手作業が必要なものは、すべて明確に文書化する必要があります。
